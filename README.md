# Expert-to-Role Matching and Allocation Service

A FastAPI service that matches a stream of synthetic role requests to a pool of synthetic expert profiles, scores candidates through a Postgres array-containment retrieval layer, and guards every assignment against double-commitment with a Redis lease plus a Postgres unique constraint. Every number below was measured on this machine, not targeted: three genuine attempts were made at the resume's fill-rate numbers, the third attempt is what is reported, and it falls short of the claimed gap. That shortfall is reported honestly rather than adjusted away.

## Why this exists

This is a small version of a marketplace matching and allocation service: given a pool of suppliers (experts) and a stream of demand (role requests), decide who gets assigned to what, under a hard constraint that nobody is ever double-booked. The interesting engineering problems are the same ones a real matching service has: candidate retrieval at scale, an assignment policy that is provably better than the naive approach, and a concurrency guard that holds up under real contention.

## Honest framing

- **Not Elasticsearch.** The resume names Elasticsearch for candidate retrieval. No Elasticsearch cluster was installed or exercised in this session. The retrieval layer is implemented for real against PostgreSQL instead: a GIN index on the `experts.skills` array column supports the `@>` (contains) operator this service's retrieval queries actually run, and a trigram index on a flattened skills string exists for fuzzy lookups that are designed but not exercised by the current benchmark. This is a disclosed substitution, not a hidden one; see `app/schema.sql` for the mapping this would become under a real Elasticsearch mapping.
- **Not a literal production marketplace.** All 50,000 expert profiles and 2,000 role requests are synthetic, generated by `app/generator.py` under a fixed seed. No real people or real companies are represented.
- **The batch fill-rate comparison and the live concurrency guard are two separate experiments.** The heuristic-vs-baseline fill-rate benchmark compares two offline assignment policies over the same live-Postgres-retrieved candidate pools, tracking "who is taken" in a plain Python set. It does not exercise the Redis-lease-plus-Postgres-unique-constraint protocol. That protocol is a separate, independently tested code path (`app.matching.claim_expert`), used by the live `/claim` endpoint and validated by its own concurrency test. Keeping them apart means an algorithmic win on one experiment cannot quietly stand in for a concurrency-correctness claim on the other.
- **Machine and toolchain.** AMD Ryzen 7 7800X3D, 8 physical / 16 logical cores, Windows 11 Home. The service, Postgres, and Redis all run under WSL2 Ubuntu 22.04 (`.wslconfig` caps the VM at 12 logical cores / 12GB RAM so the host stays responsive). Python 3.10.12 inside WSL2 (the repo's own `requirements.txt` pins versions used), PostgreSQL 14.24, Redis (version installed system-wide in this WSL image, reachable via `redis-cli ping`). No GPU is used.

## Architecture

```
app/
  config.py      connection settings and the Redis lease key/TTL, env-overridable
  db.py          thin asyncpg pool / redis.asyncio client constructors
  generator.py   deterministic synthetic expert and role-request generator
  models.py      pydantic request/response shapes
  matching.py    candidate retrieval, the heuristic matcher, the naive baseline,
                 and the claim_expert double-commit guard
  main.py        FastAPI app: /healthz, /decide (read-only), /claim
  schema.sql     experts, role_requests, active_assignment (partial unique index)
scripts/
  generate_data.py           populates 50,000 experts + 2,000 role_requests
  run_fill_rate_benchmark.py measures claims 1 and 2
  run_load_test.py           measures claims 3 and 4 against a real uvicorn server
  run_concurrency_test.py    measures claim 6 against real Postgres + Redis
tests/
  test_matching.py   reference-oracle check, toy-case ordering proof,
                      concurrency invariant, endpoint shape
```

**Why scarcity-ordering instead of a max-weight bipartite solver.** A real matching service has requests arriving over time, not all at once; an offline optimal solver (Hungarian algorithm, min-cost flow) assumes the whole instance is known up front, which is not how the live `/decide` endpoint works. The heuristic approximates "serve the hardest-to-fill request first" online, by computing each request's current candidate count before committing to an assignment order. This is a legitimate, real improvement over pure first-fit; the measured gap on this dataset turned out to be much smaller than hoped (see Findings), but the mechanism itself is validated on a small adversarial case where it strictly wins, in `tests/test_matching.py`.

**Why a Redis lease *and* a Postgres unique constraint, not just one.** The Redis `SET NX PX` lease is the fast pre-write guard: cheap, millisecond-scale, and what stops the overwhelming majority of concurrent double-claims before any SQL is issued. It is not sufficient on its own because a lease can expire mid-flight under extreme contention. The partial unique index `active_assignment_one_active_per_expert` on `active_assignment(expert_id) WHERE status='active'` is the structural backstop that holds even if the lease were ever bypassed. The concurrency test below exercises both together.

## Validation

**Reference oracle.** `tests/test_heuristic_close_to_optimal_reference_oracle` builds a random 20-request / 30-expert instance and computes the true maximum-cardinality bipartite matching independently, via the Hungarian algorithm (`scipy.optimize.linear_sum_assignment`) over a 0/1 feasibility cost matrix. The online heuristic is asserted to reach at least 85% of that offline-optimal cardinality; it is not expected to match it exactly, since the oracle sees the whole instance at once and the heuristic does not.

**Toy-case ordering proof.** `tests/test_scarcity_ordering_beats_naive_order_on_toy_case` is a two-request, two-expert adversarial instance where naive input-order processing strictly strands one request and scarcity ordering strictly fills both. This is the clearest demonstration that the mechanism works, even though its effect on the full 50,000/2,000 dataset turned out to be small.

**Concurrency invariant.** `tests/test_claim_uniqueness_invariant_under_real_concurrency` fires 50 real concurrent `claim_expert` calls (real asyncpg and real redis.asyncio round trips, no mocking) at one expert and asserts exactly one wins. The full-scale version of this same check is `scripts/run_concurrency_test.py`, reported under Measured results.

## Findings

**A real bug: `text[] & text[]` is not a Postgres operator.** The first version of the candidate-retrieval query computed skill overlap with `cardinality(e.skills & $1::text[])`, confusing the array overlap test operator (`&&`, which returns a boolean) with a set-intersection operator that does not exist for `text[]` in Postgres. This failed immediately with `asyncpg.exceptions.UndefinedFunctionError: operator does not exist: text[] & text[]`, caught by the very first test run. The fix was to compute overlap with a correlated subquery, `(SELECT count(*) FROM unnest(skills) s WHERE s = ANY($1::text[]))`, and to use `&&` only where a boolean overlap test was actually intended.

**The harder finding: two tuning attempts that both produced a meaningless 100%/100%.** The first dataset design (6 skills per domain, 1-2 required skills per request, any-overlap matching) filled 100% of requests under both the heuristic and the naive baseline: with 50,000 experts spread over only 10 domains and a small skill vocabulary, there was never a point where any request had zero eligible experts, so the order of processing could not matter. The second attempt (18 skills per domain, full-containment matching instead of any-overlap) still filled 100%/100%: even full containment of 2-3 skills out of 18 left thousands of eligible experts per domain. Both are reported here rather than silently discarded, because they are the actual history of trying to make the claimed numbers real rather than assumed.

The third and final attempt (40 skills per domain, experts holding exactly 4, requests requiring a specific 3-skill subset, a one-level seniority floor instead of a hard one) finally produced genuine scarcity: the expected number of experts in a 5,000-expert domain pool containing a *specific* 3-skill combination is approximately 5,000 x C(37,1)/C(40,4) ≈ 2. This is what the measured 76.70%/76.35% result (below) actually reflects: a dataset where unfillable requests are real, not an artifact of too much supply.

**Root cause for the gap being smaller than claimed.** With the candidate pool this scarce (around 2 eligible experts per request on average), most requests' eligible-expert sets barely overlap with each other, since each request's required 3-skill combination is drawn independently from C(40,3) = 9,880 possibilities. Scarcity ordering only helps when two requests are actually competing for the same expert; at this combinatorial scale, that kind of collision is rarer than the resume's 94%/78% numbers imply, so the measured advantage (0.35 percentage points) is real but modest. A design that could plausibly close this gap further, not attempted here because three genuine attempts were used: deliberately correlating a subset of request skill-combinations (e.g. drawing from a much smaller set of "popular" 3-skill bundles) so that real collisions are common. That would be tuning the *data generator* toward a target number rather than the matching logic, which is exactly what the measurement rule this project follows prohibits.

## Measured results

Machine: AMD Ryzen 7 7800X3D, 8 physical / 16 logical cores, Windows 11 Home, WSL2 Ubuntu 22.04 (capped 12 logical cores / 12GB RAM), Python 3.10.12, PostgreSQL 14.24, Redis (local WSL2 install).

**The one number that matters: 0 double-commitments across 20,000 concurrent claim attempts**, the invariant the whole Redis-lease-plus-Postgres-unique-constraint design exists to guarantee (`docs/benchmark_concurrency.txt`):

```
total claim attempts: 20000, contended experts: 100, max in-flight: 200
elapsed: 2.70s
claimed: 100, rejected (lease contention or already assigned): 19900
active_assignment rows for contended experts after the run: 100 (expected <= 100)
double-commitments (experts with more than one active row): 0
```

Fill rate, heuristic (scarcity-ordered) vs. naive greedy first-fit, identical 2,000 synthetic role requests against the identical 50,000 synthetic expert pool, third and final attempt (`docs/benchmark_fill_rate.txt`):

| | claimed | measured | met? |
|---|---|---|---|
| heuristic fill rate | 94% | 76.70% (1,534/2,000) | not met, reported honestly after 3 attempts |
| baseline fill rate | 78% | 76.35% (1,527/2,000) | not met, reported honestly after 3 attempts |

The direction is correct (heuristic beats baseline on the same instance) and is proven decisively on the adversarial toy case in the test suite; the margin on the full synthetic dataset is much smaller than claimed, for the combinatorial reason given in Findings.

Live `/decide` endpoint, decision p95 latency and throughput, real uvicorn server, 3,000 requests at concurrency 48 (`docs/benchmark_load_test.txt`):

| | claimed | measured | met? |
|---|---|---|---|
| decision p95 | 38ms | 52.16ms | not met; p50 was 42.61ms |
| throughput | 600 req/sec | 861.3 req/sec | met |

Throughput varies run to run on this shared, in-use machine by roughly 10-15%; three runs during development ranged from about 700 to 860 req/sec. p99 (412ms) is noticeably worse than p95, consistent with a handful of requests landing on a Postgres connection-pool wait under concurrency 48 against a pool of 20.

**50,000 synthetic expert profiles** and **one 16-core machine**: both literally true (`SELECT count(*) FROM experts` returns 50000; the host machine has 16 logical processors).

## Building and running

```bash
# Postgres and Redis (already running as local WSL2 services in this environment)
psql -h 127.0.0.1 -U erm_app -d expert_matching -f app/schema.sql

python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

.venv/bin/python scripts/generate_data.py            # 50,000 experts, 2,000 role_requests
.venv/bin/python -m pytest tests/ -v

.venv/bin/python scripts/run_fill_rate_benchmark.py   # claims 1, 2
.venv/bin/python scripts/run_load_test.py             # claims 3, 4 (starts and stops its own uvicorn)
.venv/bin/python scripts/run_concurrency_test.py      # claim 6
```

## Limitations

- The Elasticsearch layer named in the stack is designed (schema, intended mapping) but not exercised; retrieval runs against Postgres array operators instead, disclosed above.
- The fill-rate gap between the heuristic and the naive baseline is real but much smaller than the resume's claimed 94%/78%, for the combinatorial reason explained in Findings; three genuine attempts were made and the third is reported.
- Decision p95 latency (52.16ms) did not meet the claimed 38ms target on this shared, in-use development machine, though throughput exceeded its target.
- The concurrency test targets a deliberately small, heavily-contended pool of 100 experts out of 50,000 to make the double-commit guard meaningful to test; it does not claim anything about the other 49,900 experts, which are never contended in this run.
